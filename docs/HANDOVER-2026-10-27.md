## 0. Read this first (one page)

1. **What it is.** A multi-tenant (one `Workspace` per customer store) sales-and-replies platform for cash-on-delivery commerce in Syria/Jordan. Customers write on Facebook Messenger, Instagram, WhatsApp, Telegram or TikTok. An AI agent (الوكيل الذكي) answers using a persona (الشخصية), a knowledge base (المعرفة) and the product catalogue, can build an order draft, and staff can take over. Next.js 14 App Router, RTL Arabic, Prisma + PostgreSQL (pgvector), zod, Vitest.
2. **What was just done.** The whole navigation and flow was restructured for "smoothness": 26 tabs became 21, duplicate pages merged, every dead-end button fixed, Arabic labels everywhere, an in-site guide and a guided tour added. All of it is merged to `main` (PR #1 on the fork). 99 test files / 1,533 tests, typecheck, lint, secret scan and build all pass, and GitHub CI is green. Details: section 3.
3. **What was NOT done.** Nothing that was asked is half-built, but a full review (code structure, logic, calculations, permissions, security) was run **after** the restructure and found real defects that are **not fixed**. Section 4 is the plan. This document is the review's deliverable; no defect has been fixed yet.
4. **Two critical security defects.** (a) *Cross-tenant account takeover*: anyone can self-register, invite any existing user's email into their own workspace, and then set that user's global password (S-01). (b) *Server AI key leaks*: a workspace can point the `hermes` provider at an attacker URL and the platform-wide `HERMES_API_KEY` is sent there (S-02). **Do not put real customers on a public deployment until S-01, S-02, S-03 and S-11 are fixed.**
5. **Two critical money/behaviour defects.** The yes/no parser misreads everyday Arabic: «يلا أكد الطلب» cancels the cart and «أي لون عندكم؟» places an order (L-01; I reproduced this). Quantity words are matched as substrings, so «بدي عشرين» means 10 and «الاثنين» (Monday) means 2 (L-02), and a chat can rewrite a placed order's quantity with no rules and no confirmation (L-03).
6. **The project's own rule files are partly stale.** `AGENTS.md`, `docs/INTEGRATIONS.md`, `docs/OMS-DOOR-V1.md` and `contracts/README.md` describe the OMS module, the agent door and signed OMS events as live. They were **deleted** on 2026-10-18 (commit `3c3c4aa`, "AI-only response system"). Trust the code, not those files, for anything OMS/agent-door. Fixing the docs is task D-01.
7. **The handoff queue is always empty.** The same commit made the AI never create a human handoff (`HumanHandoff`), and no production code calls `createHandoff` (only tests do). The page `/handoffs` ("تحتاج موظف") and the dashboard KPI "يحتاج موظف" therefore show nothing. This is a product decision for the owner (section 4.5, OD-1).
8. **The running site on `localhost:3250` is an old build** (from `C:\Users\LOQ\Documents\AIresponse-work\AIresponse`, 6 commits behind). It does not contain the restructure. Rebuild from this tree to see it.
9. **Account situation.** The restructure lives on `iahmed30004000-wq/AIresponse` (private). The canonical repo `MKory18/AIresponse` (public) does **not** have it yet. Section 1.
10. **Working rules that cannot be broken:** branch + pull request, never push to `main`; a test that fails before and passes after every fix; all five gates green; CI is the judge. Section 10.

### 5.3 Request lifecycle
`createHandler(options, fn)` (`src/core/api/handler.ts`) in order: (1) CSRF — for POST/PATCH/PUT/DELETE, if an `Origin` header exists its host must equal `Host`, else 403 `CSRF_REJECTED` (no Origin passes: Meta, server-to-server); (2) `Content-Length` > 110 MB → 413; (3) optional DB rate limit keyed `ip:path` (`rateLimitStrict` fails closed 503); (4) auth — unless `public:true`, `getAuthContext()` loads the user and the **ACTIVE** `WorkspaceMember` fresh from the DB on every request and `auth.require(permission)`; (5) zod `body`/`query`. Errors map: `ZodError` → 422 `VALIDATION_ERROR`; `AppError` subclasses → their code (401/403/404/409/429/502…); anything else → 500 `INTERNAL_ERROR`. 26 routes bypass `createHandler`: analytics (`analyticsRoute` wrapper, `analytics.read` default), webhooks, health, `media/public/[token]`, the Facebook OAuth callback, `/api/v1/*` (`createSystemHandler`, scoped tokens).

### 5.4 Inbound message pipeline
Webhook route (`api/webhooks/{meta,whatsapp,instagram,telegram,tiktok}`; HMAC / secret verified) → ingest in one transaction (idempotent `WebhookEvent` row + enqueue a job; Facebook uses `process_webhook_event`, others `process_channel_inbound`) → job handler resolves tokens/profile → `processIncomingMessage` (`conversations/inbound.ts`): customer resolve via `ChannelIdentity`, conversation find/reopen, persist `Message`, publish events, then by `Channel.sendMode`: `COLLECTION_ONLY` → `extract_customer_intel`; `AUTO_REPLY` with `aiState=AI_ACTIVE && aiEnabled` → `process_ai_message` → `processAIMessage` (`ai/orchestrator.ts`): gating (idempotency, state, ordering guard, provider) → extraction (intent/entities, injection screen, order intent, RAG, plan) → response (`sendProtectedText` privacy gate, `validateResponse` guardrails with one regeneration then safe fallback, send, usage log, citations) → `dispatchOutbound` (`send-policy.ts` re-reads `sendMode` at send time; idempotency key `conversationId:sourceMessageId`; per-channel policy incl. the Messenger 24-hour window and WhatsApp window/templates). **The AI path never creates `HumanHandoff` rows.**

### 5.5 Background jobs and worker
`BackgroundJob` model; 18 job types in `JOB_TYPES` (`jobs/service.ts`): knowledge docs, feedback, media, AI message, summary, webhook/channel inbound, WhatsApp media, automation, follow-ups, analytics aggregate, workflow events/resume, campaign run/tick, attribution validate, product compliance, customer intel. `processPendingJobs`: recover stale (10-min lease) → recover stuck outbound → recover orphaned inbound → atomic claim → run with timeout (`JOB_TIMEOUT_MS`, 120 s) → exponential back-off 30 s…10 min, 3 attempts. Worker (`npm run worker`): loop of `runJobs` (limit 25), `processDueFollowUps`, `runIntegrationScheduler`; poll 1,000 ms (min 250); SIGTERM-safe; no health check (liveness only via the `worker_started`/`worker_heartbeat` log lines). Cron alternative: `POST /api/jobs/run` with `x-jobs-secret`. **The event bus is per process:** the automation and workflow bridges are registered in `scripts/worker.ts`; `/api/jobs/run` registers only the automation bridge; whether events published from Next.js routes reach workflow triggers is **UNVERIFIED**.

### 5.6 RBAC
Roles `UserRole`: SUPER_ADMIN, OWNER, ADMIN, MANAGER, SALES_AGENT, SUPPORT_AGENT, VIEWER. 46 permissions in `src/modules/rbac/permissions.ts`; `ROLE_PERMISSIONS` (SUPER_ADMIN/OWNER/ADMIN all; MANAGER all except `users.manage`, `workspace.manage`; agents read-mostly). `WorkspaceMember.permissions` can only **add** permissions. Owner-only actions use `requireWorkspaceOwner`. The team page matrix (`components/role-matrix.tsx`) is generated from `ROLE_PERMISSIONS`.

## 7. KPI catalogue — how each number is computed today (owner rule: every KPI states its rule)

All counts are per workspace. Range is `[start, end)` with day boundaries in the time zone the user picks (default UTC — L-19). "Confirmed set" = order status CONFIRMED, PROCESSING, OUT_FOR_DELIVERY or DELIVERED, judged by the **current** status. Money = sum of `Order.total` (= items − discount + delivery fee), **no tax**, and currently **summed across currencies (L-08)**.

**Dashboard:** محادثات = conversations created in range · طلبات = all orders created in range · عملاء جدد = customers created in range · **التحويل** = orders created in range in the confirmed set ÷ conversations created in range × 100 (different populations — L-16) · رسائل الذكاء = AI usage-log rows (calls, including failed) · يحتاج موظف = handoffs created in range still OPEN (always 0 in production — OD-1) · طلبات/إيرادات مؤكدة and مُسلَّمة = orders created in range in the confirmed set / DELIVERED, and their `total` sum · نشطة = conversations OPEN right now (not range-limited) · رسائل واردة/صادرة = messages by direction in range (notes included here, excluded in trends) · استدعاءات فاشلة = usage rows with `success=false` · توكنز = prompt + completion tokens · التكلفة التقديرية = sum of known `costUsd` (null only if every call unknown; a partial sum shows without a warning) · إجمالي التحويلات = handoffs created in range · متوسط زمن الحل = mean(`resolvedAt − createdAt`) over handoffs with `resolvedAt` (includes cancelled) · تنفيذات/ناجحة/فاشلة/متجاوزة = automation execution rows by status (skipped checks count as executions).

**Reports tab:** *Funnel* (محادثات → مسودات → جاهزة → مؤكدة → مسلَّمة) = conversations created; drafts created whose current state is not EMPTY; drafts in READY/CONFIRMING/CONFIRMED/CONVERTED (current state — L-17); confirmed orders; delivered orders; each rate = stage ÷ previous, null when the denominator is 0. *Comparison %* = (current − previous) ÷ previous × 100, «جديد» when previous is 0. *Conversations*: first-response time = minutes from first inbound to first outbound (AI, human or automation) per new conversation, notes/deleted excluded, unanswered excluded; resolution time = `updatedAt − createdAt` for RESOLVED/CLOSED (L-21). *Sales*: counts by current status; قيمة مؤكدة = sum of `total` over the confirmed set; average = that ÷ confirmed count; offer acceptance = OFFER_ACCEPTED ÷ OFFER_SHOWN events in range (no dedupe — L-23). *Products*: units = sum of item quantity over confirmed orders created in range; revenue = item `subtotal` (price × qty, **before** discount and delivery — will not match قيمة مؤكدة). *Agents*: assigned conversations, human outbound replies, median first response, linked orders, handoffs, approved discounts (audit `sales.discount_approved`). *AI*: calls/success/failure, tokens in/out, average `latencyMs`, cost. *Campaigns*: status of all campaigns (not range-limited), distinct recipients, SENT (platform accepted), confirmed delivered (DELIVERED/READ). *Automation*: completed/failed per rule, success = completed ÷ (completed + failed). *Trends*: one row per **UTC** day, only rows with status OK (L-18). **CSV export** uses the same functions as the screen; the "Excel" button actually downloads CSV.

## 10. How to work in this repository

**Gates before every commit** (all must pass): `npm run typecheck` · `npm run lint` · `npm test` (≈1,533 tests, in-memory DB, no Postgres needed) · `npm run scan:secrets` · `npm run build`. In an environment without the Prisma engine, one `PrismaClientInitializationError` per test file is expected; CI does not show it. CI (`.github/workflows/ci.yml`, Node 22): job `verify` (the five gates with dummy env) and job `migrate-check` (`prisma migrate deploy` on real pgvector Postgres — it does **not** check schema drift; adding that is a good small task).

**Process.** New branch from an up-to-date `main`; failing test first; fix; gates; PR; wait for green CI; merge. Never push to `main`. Schema change = additive migration only (no drops, no type changes). Any new dashboard page needs: a `NAV_GROUPS` entry, `PAGE_KEYWORDS` (`src/lib/nav-search.ts`) and a `PAGE_GUIDES` entry with a valid "next" page — or `tests/nav-structure.test.ts`, `nav-search.test.ts`, `page-guides.test.ts` fail. Any displayed enum needs an Arabic `LABELS` entry (`tests/labels-arabic.test.ts`). Any new media query must go through `excludeCustomerInbound()`. Any new idempotency key includes the workspace. Any new secret field uses `PasswordInput`. Never write "Hermes" in visible text. Theme colours only from CSS variables.

**Communication with the owner.** Jordanian Arabic, short, no jargon; written deliverables as `.docx` + PDF; risks in red with the fix in orange.
